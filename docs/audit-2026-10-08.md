## Fixed in this pass

1. **Sign-in throttle never reset on success when signing in by email/phone.** Failures were stored under the canonical login but cleared under the typed one, so scattered typos accumulated and could lock out a legitimate user. `controllers/main.py` now clears the canonical key. Verified live.
2. **A bare negative quantity was accepted as a "return".** A cashier could post a line with `qty < 0` and no `refund_of_line_id`, paying cash out and adding stock with no original sale. `sale_service._prepare_lines` now rejects it ("Use Return on the original bill"). Regression test `test_07b_bare_negative_quantity_is_not_a_return`.
3. **`/api/sync/delta` and `/api/sync/flush` answered 500 on malformed input** (`since_seq=abc`, a list body, a mutation missing `device_seq`). They now answer 422 with a clear message.
4. **Session cookie now carries an explicit `SameSite=Lax`** (AGENTS.md section 4 item 5; `Secure` and `Domain` are added by Caddy in `deploy/Caddyfile`).

## Not fixed: bigger or needs an owner decision (pick up here)

| # | Finding | Why it matters | Suggested next step |
| --- | --- | --- | --- |
| A | **Purchase create can double-post on an ambiguous response.** `frontend/src/lib/repo.ts` `createPurchase` calls `record_bill` directly with `v.idempotency_key \|\| crypto.randomUUID()`, and `PurchasesPage.tsx` (around line 1466) never passes a key. A timeout after the server committed, followed by the user pressing Save again, creates a second bill. The server only dedupes on `client_ref` (no supplier + invoice-number guard). | Real money and stock, double stock-in. | Generate the key once per form instance (ref created when the form opens, reset on success) and/or route purchases through `submitMutation('purchase', ...)`. Consider an Odoo-style duplicate warning for the same supplier + non-empty supplier invoice number (owner decision: warn or block). Add a test. Same pattern exists for purchase returns (`PurchasesPage.tsx` around line 598). |
| B | **Any cashier can override the unit price on a sale.** `sale_service._prepare_lines` has `override_ok = True` hard-coded. | Retail counters often allow it, but there is no role or setting behind it. | Owner decision: add a per-role / Business Studio permission ("price override") and a discount cap, enforced server-side. |
| C | **Device sequence counter is not atomic with the IndexedDB enqueue** (`frontend/src/lib/sync.ts` `nextDeviceSeq` uses `localStorage` plus `outbox`). Two tabs enqueuing at once can pick the same number; one then stays `out_of_order`. Already listed in HANDOFF section 5.C.8. | Offline sales stuck until fixed. | Allocate the sequence inside a Dexie transaction on a counter table, or use a Web Lock around allocate + put. |
| D | **Login failure counter is a read-modify-write** (`models/login_throttle.py` `record_failure`: `row.failures += 1` on a separate cursor). Parallel guesses can under-count. | Weakens the 5-attempt limit under concurrency (still bounded by the 5-minute window). | Single `UPDATE ... SET failures = failures + 1` (or `SELECT ... FOR UPDATE`). Same code exists in the platform copy. |
| E | **Two identical `Set-Cookie: session_id` headers** are sent on login. | Harmless today; the proxy rewrite in `deploy/Caddyfile` regex-matches each. | Check Odoo's own cookie write vs `_issue_cookie`; send one. |
| F | Items already known and listed in HANDOFF section 5 (10,000-shop capacity, plan contents, production host and restore drill, disabled retailer features, browser test for `/dev`, role isolation in the browser) were **not** re-examined here. | | See HANDOFF. |
